# Prefilter: domain adaptation against a matched control

Two prefilter runs that differ **only** in `domain_adaptation.lambda_scheduler.max_lambda`:

| model | run | max_lambda |
|---|---|---|
| DA | `da_prefilter_numu_260429_0155_Qclip_softlabels_PlateauLR_lambda0.05_MC2M_dmodel128_zflipBothMCExp_SoftFocalLoss` | 0.05 |
| control | `da_prefilter_numu_260428_2039_Qclip_softlabels_PlateauLR_lambda0.0_MC2M_dmodel128_zflipBothMCExp_SoftFocalLoss` | 0.0 |

A diff of the two `da_config.yaml` files shows that key, the run name and the training
GPU, and nothing else — same seed 42, same architecture, same NPY source dataset, same
`exp.h5` target, same losses and schedules.

## Files

| file | what it does |
|---|---|
| `run_scoring.sh` | the exact scoring commands: mc_merged for the control on the parts the DA model already covers, then exp_full for both models over all 29 parts |
| `report_lib.py` | loading, metrics and every figure, on top of `inference.reader` |
| `compare_lambda0.05_da.ipynb` | DA model primary, control drawn as a halo on each figure |
| `compare_lambda0.0_control.ipynb` | the same figures with the roles swapped |
| `make_notebooks.py` | generates both notebooks from one template — **it overwrites them**, so notebook prose is edited here |
| `test_metrics.py` | checks the metric core against brute force over 36 configurations, ties included |
| `scored_parts/` | the per-class h5 part lists `run_scoring.sh` read out of the DA model's database, so the control was scored on the same parts |
| `figures/` | output; regenerated by running either notebook end to end |

Run order: `bash run_scoring.sh`, then either notebook. `python test_metrics.py` checks the
metric core on its own and needs no data.

Only the code is under git: `.gitignore` keeps `scored_parts/`, `figures/` and the
prediction databases out, which is why the notebooks regenerate the figures rather than
ship them.

## The working point is a cut, and cuts are made of distinct scores

`suppression = 1e-3` is met by the **loosest** threshold whose own pass fraction is at
most 1e-3 — loosest, because any tighter one also respects it while throwing away signal
for nothing. Only distinct scores are candidates: a threshold cannot split events that
share a score, so reading the running cumulative alone would name a threshold that
overshoots by the weight of the tie block it landed inside. `test_metrics.py` is mostly
about that case. The achieved suppression is printed beside the threshold in every
notebook, so an unreachable target would be visible rather than assumed away.

## Reading the data

Everything goes through `inference.reader`. Zenith angle, primary energy and the MC event
weight are not in the catalog — they live in `prime_prty` in `baikal_mc_merged.h5`, and
the reader returns them as `prime_theta_deg`, `prime_energy_gev`, `prime_event_weight`.
`exp_full` is never materialised: its 133M scored events are read only through
`Reader.histogram`, which bins them inside DuckDB.

Two additions were made to the reader for this report, both with tests in
`inference/reader/tests/test_reader.py`:

* `reader.NOT_TRAINED_PARTS` (`training.part_identity`) — a part-level training
  exclusion, for datasets that record no per-event back-links. The prefilter builder
  writes no `h5_part_keys.npy`, so its `build_config.yaml` part list is the finest handle
  there is. Asking for a finer strictness on such a dataset now raises and names this one,
  instead of quietly excluding nothing.
* `Reader.histogram(...)` — bin a per-event column in DuckDB without materialising rows.

## Out-of-training

**MC** — `NOT_TRAINED_PARTS` drops all 952 parts the training dataset was built from
(432 muatm, 187 nuatm, 333 nue2). Of the scored parts that leaves 31,283,901 of
39,169,783 events: muatm 21,079,081, nuatm 8,912,750, nue2 1,292,070. Coarser than the
nu-classifier's per-event exclusion and strictly safer — a part the builder never opened
cannot have contributed an event.

**exp_full** — the DA target of both runs was `exp.h5`, whose 26 runs are disjoint from
the 29 runs in `exp_full.h5`; no part key appears in both. The notebooks check this rather
than assert it.

## Caveats carried onto the figures

* **Weights.** `EventWeight` is applied within a class only, so the metrics stay defined
  whether or not it is comparable between muatm, nuatm and nue2 — that comparability is
  `assumed`, not checked. Weighted and unweighted panels are drawn side by side.
* **`nue2` is astrophysical nu_mu with an E^-2 spectrum**, not electron neutrinos.
* **No live-time normalisation** exists for this MC, so the experiment-over-MC figure is a
  shape ratio and its absolute level is not a rate.
* **The MC classes occupy disjoint zenith hemispheres** — muatm 94.2-179.9 deg, both
  neutrino classes 0.11-90.00 deg with the cap at exactly 90.00. So in this MC no
  atmospheric muon and no neutrino share a zenith angle, and the separation the figures
  show is easier than a real sample would offer. Logged in `doc/claims_log.md`.
* **Two exp_full runs** (`part_s2020_c02_r0020`, `part_s2020_c02_r0249`) are dropped by
  `reader.NOT_EXCLUDED` — four channels emitting up to 3169.8 p.e. against a median hit of
  0.97, evidence in `inference/reader/spec.py`. `EXCLUDE_BAD_EXP_RUNS` at the top of each
  notebook turns this off; the counts both ways are printed either way.
