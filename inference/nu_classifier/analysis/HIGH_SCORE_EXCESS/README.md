# HIGH_SCORE_EXCESS: анализ избытка высокого скора

Каталог содержит два типа анализа распределений и отборов по чекпоинту:

| Тип | Что делает | Данные |
|---|---|---|
| `full_score_range` | воронка отборов, доля сошедшихся фитов, распределения по всему скору | фиты BARS + `catalog_v2` + prediction-БД |
| `high_score_range` | яркая часть скора, DQM-фильтр, признаки из хитов, фит BARS | те же источники + кэш parquet |
| `survival` | кривые «доля с logit > порога» по классам и отношение exp/muatm | только prediction-БД + reader; без хитов и фитов, без кэша |
| `tracknn` | угол, точка на линии, сырые sigma и качество track NN для хвоста exp-скора | classifier-БД + track-NN DuckDB + 10% test-MC; без хитов и BARS-фитов |

## Как устроено после рефакторинга (2026-10-25)

```
template_full_score_range.ipynb    шаблон: параметры + обвязка вызова
template_high_score_range.ipynb    шаблон: параметры + обвязка вызова
template_score_survival.ipynb      шаблон: кривые выживания скора без фитов
template_tracknn.ipynb             шаблон: classifier score + track-NN, без BARS-фитов
make_notebook.py                   генератор пер-чекпоинтных ноутбуков
by_checkpoint/<checkpoint>__<type>.ipynb   созданные ноутбуки (свои ячейки/выводы)
excess/                            общий код
  full.py     загрузка кадра событий (фиты + каталог + скоры), quality/by_class
  high.py     домены, отбор, DQM-фильтр, кэш parquet + manifest, фит BARS
  survival.py все проскоренные test-МК и exp события через reader.events
  tracknn.py  classifier-события + track-NN DB, домены/прореживание/derived, без фитов
  features.py признаки из хитов: per_event_features, signal_hit_geometry, производные
```

Вся тяжёлая обвязка живёт в `excess/`; в ноутбуках остались только параметры и
ячейки анализа. Различия между пер-чекпоинтными ноутбуками — в ячейке параметров
и в правках анализа (маски, диапазоны, дополнительные графики); их можно менять
локально, не трогая остальные ноутбуки.

## Support vs measure (2026-11-08)

| файл | что делает |
|---|---|
| `support_vs_measure.py` | kNN-покрытие exp-хвоста относительно muatm MC по сырым признакам; по умолчанию только хиты, принятые SN-моделью (prob > 0.8) |
| `excess/raw_features.py` | расширенные признаки: заряд, время, световая кривая, форма трека, фиты z/x/y(t), занятость каналов/модулей, корреляции заряда с координатами |
| `measure_feature_shift.py` | одномерные AUC по признакам и многомерная разделимость по группам; low-score контроль глобального доменного сдвига |

Артефакты: `data/support_vs_measure_signal*_h8s3_muOnlyDA_e23_tail0.json`,
`data/support_vs_measure_signal_expanded_loo_h8s3_muOnlyDA_e23_tail0.json`,
`data/feature_shift_signal_expanded_h8s3.json`,
`data/features_signal_expanded_h8s3.parquet` (кэш 117 845 событий, 194 колонки).
Leave-one-group-out (`--loo`): полный набор 0.029; без `basic` 0.019, без
`charge` 0.024, без `occupancy` 0.026, остальные 0.026–0.033. Ни одна группа
не несёт support — вклад мал и размазан.

**Результат (h8s3 e23; статус `consistent`, не `verified`).** После перехода на
SN-хиты support-вклад мал: на 25 базовых event-признаках — 0.9 %, на 122
расширенных признаках без геометрии струн — 3.4 % (exp tail 2.28 % outside,
exp low 1.60 %, MC 1.0 %). Разница tail−low +0.67 п.п. (z≈3.5) мала; большая
часть outside-доли есть уже при низком скоре, то есть это глобальное доменное
различие, а не свойство хвоста.

Геометрия струн — глобальный сдвиг: в MC струны строго вертикальны
(`string_tilt_*` ~1e-14°), в exp ~0.25°. До исправления масштабирования
(деление на СКО ~1e-14) она давала 100 % outside — это артефакт; после
исправления 3.6 % (tail) против 3.1 % (low).

Наиболее tail-специфичны время и световая кривая. В exp high-score события уже:
`t_qstd` 61.8 против 68.8 нс, `t_span` 273 против 291 нс в MC tail; при низком
скоре exp и MC совпадают в пределах ~2 нс. В MC скор почти упорядочен по этим
признакам (AUC 0.95–0.97), в exp — заметно слабее (0.59–0.64). Это гипотеза
measure/response-механизма, а не доказательство причины.

Ограничения: kNN-покрытие — операционный прокси, не теоретический support;
одномерные AUC-различия малы (0.54–0.59); score — не физическая метка;
exp_low и mc_bg — выборки (10k/50k), а не полные популяции. Прежний результат
по всем хитам (event outside 7.9 %, low 6.8 %) включал шумовые хиты и как
основной больше не используется.

Производительность чтения (12 воркеров, холодный кэш): MC — по-событийно
158 ev/s против 36 ev/s целой частью; exp — целой частью 65 ev/s против
58 ev/s по-событийно. Поэтому whole-part включается только при >= 25
выбранных событиях в части.

## Новый чекпоинт

```bash
python -m inference.nu_classifier.analysis.HIGH_SCORE_EXCESS.make_notebook \
    --checkpoint <имя_каталога_в_preds> --type full   # или high
```

Ноутбук появится в `by_checkpoint/`. Существующий файл не перезаписывается без
`--force`. Для `high` можно сразу попросить пересборку кэша: `--force-reload`.

Для `tracknn` нужны две track-NN БД (exp и MC), построенные на том же наборе
событий, что и classifier-предсказания:

```bash
python -m inference.nu_classifier.analysis.HIGH_SCORE_EXCESS.make_notebook \
    --checkpoint <имя_каталога_в_preds> --type tracknn \
    --track-db-exp <...>/exp_full_canonical_p070_track.duckdb \
    --track-db-mc  <...>/mc_merged_canonical_p070_track.duckdb
```

BARS-фиты и `cached_data/` в этом варианте не используются: `tracknn` читает
только classifier-БД, track-NN DuckDB и (для MC) per-event скаляры из HDF5.

## Кэш

`cached_data/<checkpoint>/` — parquet-файлы доменов и фита плюс `manifest.json`.
Кэш проверяется при чтении: чекпоинт, условия отбора, метка DQM-фильтра и набор
колонок. В манифесты, записанные начиная с 2026-10-25, дополнительно входит
идентичность prediction-БД (путь, mtime, размер), поэтому перезапись DuckDB под
тем же именем чекпоинта автоматически инвалидирует кэш. Старые манифесты
продолжают читаться.
