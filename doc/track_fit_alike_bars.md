# The ported BARS track fit

`inference/track_fit_alike_bars/` re-implements the muon-track reconstruction of BARS
**v2.3.2** in Python, so that this project can fit its own events and cut on the quality
of the result without going through the BARS production.  It is a port, not a wrapper:
the sources it follows are named in the package's README, module by module.

It exists to answer one question — whether the two-stage selection still holds up after
quality cuts.  The cuts themselves are a separate decision.

Nothing here changes what the existing files say about BARS: `reco_quality_cuts.md`
describes the cuts applied to BARS' own output, and this page describes a second
implementation of the thing the cuts are applied to.

## What it produces — **verified**

`TrackFit` mirrors the fields the analysis cuts use, with snake_case names and a mapping
dict (`BARS_NAMES`) to the `BRecoMuon` field each reproduces:

| ours | BARS | unit |
|---|---|---|
| `theta_rec`, `phi_rec`, `theta_err`, `phi_err` | `fThetaRec`, `fPhiRec`, `fThetaErr`, `fPhiErr` | degrees |
| `scf_theta`, `scf_phi`, `scf_max_theta`, `scf_min_theta` | `fScfTheta`, `fScfPhi`, `fScfMaxTheta`, `fScfMinTheta` | radians |
| `func_value`, `time_chi2`, `charge_term` | `fFuncValue`, `fTimeChi2`, `fChargeTerm` | — |
| `n_hits`, `n_strings`, `n_oms`, `n_triplets`, `z_dist`, `ev_center_z`, `p_hit` | `fNHits`, `fNStrings`, `fNOMs`, `fNTriplets`, `fZDist`, `fEvCenterZ`, `fPHit` | — |
| `n_calls`, `cov_matrix_status`, `min_status` | `fNCalls`, `fCovMatrixStatus`, `fMinStatus` | — |
| `q_acc_20`, `q_tot_20`, `t_res_30_med`, `log_phit_30_min` | `BRecoMuonBDTEval` | p.e., ns, log₁₀ |

`theta_rec` is the polar angle of the direction of **motion**: below 90° is up-going.
`status` says where the chain stopped (`ok`, `no_clique`, `no_global_trigger`, …) and the
scalars are `NaN` when it did not reach the end.

## What is established, and against what — **verified**

The reference is BARS' own reconstruction of the same pulses: the reco HDF5 files carry
both the pulses and the `BRecoMuon` written for them, and the ROOT files carry the
`ScanfitMask` and the DQM channel mask that were the *input* to that reconstruction.  So
the port can be fed exactly what BARS was fed.  Measured by `validate_vs_bars.py` on
2000 `exp_reco` events drawn from 200 runs, and 1000 `mc_reco` muatm events from 100 parts:

* the **hit selection is identical**: the scanfit mask agrees event for event in **100.0%**
  of both samples once the DQM mask is supplied (93.4% without it), and `scf_max_theta`
  likewise;
* after the scanfit the port reproduces `ScfTheta`, `FuncValueScf` and `TimeChi2Scf` to
  1e-3 in 100% of events, `ThetaInit` in 91% and `ThetaRec` in 86% (median relative
  difference 1e-4), measured on BARS' ROOT file in `tests/stage_diagnostics.py`;
* every preliminary cut of the analysis tree gives the **same decision** per event in
  85–100% of events (97–100% for all but `covMatrixStatus`).

## The chain, drawn

![The BARS v2.3.2 reconstruction chain and where the port can differ](../inference/track_fit_alike_bars/figures/reconstruction_chain.png)

Every box is a BARS task with a status chip: **identical, checked** (green), **reproduced,
but fragile** (amber — the step itself matches, but it is a discrete decision that
amplifies any difference in the fit), **can differ** (red).  The coloured dots name the
*hit set* a box produces, and the same dot reappears in the table at the bottom, which is
the point worth carrying away: the quantities the analysis cuts on are **not** all computed
from the same pulses.  `q_tot_20`, the paired-pulse test, `t_res_30_med`, `log_phit_30_min`
and `ev_center_z` never look at the fit at all — they are event-level; `q_acc_20` is summed
over the **scanfit** mask; only `z_dist`, `nTriplets`, `pHit` and the angles themselves come
from the final fit set that `fNHits` counts.  `fNHitsInit` and `fNHitsRecoll` are further
counts of other sets again (before the removal, and after a wider second collection that
feeds only the energy estimate).  The picture is generated by
`inference/track_fit_alike_bars/make_chain_figure.py`; the figure itself is not under git
(`*.png`), the script is.

## The DQM channel mask, and where it comes from — **verified**

BARS reconstructs experimental data with `Mask.UseDQMChannelMask 1`.  The mask is in
neither the HDF5 nor the reco ROOT `reco_prty`; it is `BApplyDQMMask`'s output, and
supplying it is what closes the last 6.6% of the hit selection.

`BApplyDQMMask` builds it from the per-run solution file `j{run}.fit.solution.txt`
(`DQM_FIT_SOLUTION`, dqm-version v1.3, code 0/1/4/7/10 → masked) intersected with a
per-event section mask.  The Gantt histograms are read only when `Mask.UseGantt` is set,
and it is **0** in every 2020 resource file.

* The solution file of `c01/r0027` reproduces the ROOT `ChannelMaskDQM` container exactly:
  the same 40 channels, event after event.
* On the eleven `exp_reco` runs where both are unpacked, every channel the solution masks
  is also masked in the container.
* The container masks more only where the section mask moves; over those eleven runs that
  part touches **0–0.2% of hits** (0 in eight of them), so the run-level solution file is
  enough for the `exp_full` sample, for which it exists for **all 29 runs**.

`masks.py` reads both.  MC needs neither: `UseDQMChannelMask` is 0 for MC.

## `fEvCenterZ` is in the frame of the input, not of the detector — **verified**

BARS writes `fEvCenterZ` in the frame of its geometry.  Measured against the port, whose
value is in the frame of the hits — median |difference|, 2000 `exp_reco` and 1000
`mc_reco` events:

| file | our value as it is | our value + cluster centre |
|---|---|---|
| `exp_reco.h5` | 361 m | **1.8e-5 m** |
| `baikal_mc_reco.h5` | 1.1 m (90%: 42 m) | 0.67 m (90%: 43 m) |

For the experimental files the difference *is* the cluster centre (≈ 360 m) and adding it
closes the comparison to 2e-5 m — **verified**.  The `-354` the analysis tree applies for
data is therefore not needed with these files, and `fEvCenterZ < 220` means different
things in the two frames unless the frame is stated.  This is the same effect
`reco_quality_cuts.md` records as a "frame mismatch", measured here from the other side.

For the MC files the cluster centre is ≈ 0.4 m, so neither column is the other one plus a
constant: the residual ~1 m is unexplained — **consistent**, not verified.  The tail is
expected in any case, because an `mc_reco` row is one cluster's piece of an event that may
have lit several, while `fEvCenterZ` is an event-level field.

## What does not agree, and why — **verified as a disagreement**

The chain agrees; the **minimiser** does not.  BARS minimises with ROOT's Minuit2, the
port with iminuit, and on a flat functional with 8–16 hits a different path lands in a
different local minimum.  The convergence tolerance is not the cause: refitting the same
events with tolerances from 5 down to 0.01 moves the port away from BARS, not towards it
(86% of directions within 1e-3 at tolerance 5, 77% at 0.01).  What the disagreement is:

* on events whose hit sets agree and whose directions differ by more than a degree, the
  port's χ² is **lower** than BARS' in 69% of cases — it is not the worse of the two;
* lower χ² here means a different minimum of the *same* functional, not a different
  objective: recomputing the port's own χ² at BARS' track (its `xyzRec_*`/`dirRec_*`
  shifted into the frame of the hits, the time profiled out on both) reproduces BARS'
  `fTimeChi2` to a median relative difference of **1e-5**, so functional, hit set and
  frame are shared; the port's track is lower in 55% of 2000 `mc_reco` events, 76% of
  those where the directions differ by more than a degree;
* "lower in 55%" and "the median ratio is 1.0000" are not in conflict, they are two
  different statistics: in most events both fits end in the same minimum and the ratio
  is 1 to a few parts in 10⁴, which is all a median reports; the sign is decided by the
  minority where the two land apart, and there the ratio is far from 1;
* and against **MC truth**, which neither fit sees, the port is if anything the better
  of the two: on the 191 events of that sample with a single muon, its direction is
  closer to the primary particle's in 57%, and in 61% of the 56 events where the two
  disagree by more than a degree (median error 7.4° against 9.6°).  The tail is where
  the functional is flattest — the rate of |Δθ| > 1° falls from 24% at 5–8 hits to 6%
  at 18–30 — so a lower χ² there is not a better direction, just a different one.  See
  `inference/track_fit_alike_bars/tests/truth_check.py`;
* `n_calls` and `covMatrixStatus` are counters and states of a different minimiser, so
  they are not comparable at all (the agreement of `n_calls` is 1%).  A cut on `nCalls`
  has to be calibrated in the port, not copied;
* a hypothesis that the difference comes from `Float_t` arithmetic — BARS stores its
  `double` intermediates as `float` — was tested by emulating the C++ types through the
  fit and **refuted**: the agreement did not improve.

Two smaller gaps: the port is written against **v2.3.2** while the reco files do not
record which version produced them, and the per-event section part of the mask cannot be
reproduced locally (measured above at 0–0.2% of hits).

## The isolation variable (`pnonhit`) — **verified**

`geometry.py` and `isolation.py` answer a question the fit itself never asks: how
likely the modules around the fitted track were to fire, and how well the track
explains the silence around it.  The reference is BARS' own `fPnonHit`
(`BMuonCandidate::GetPnonHitProd`): for every OM within 22 m of the track that did
not contribute a hit, the probability it stays silent under the track's light
model, geometrically averaged.

**Where the geometry comes from.**  Not from the HDF5: the layout stores positions
only for hit channels, and a silently-lying OM has none.  The production geometry
is the `BGeomTel.fOMs.fPosition` branch of the ROOT files, and it is stored **per
event**: on `c04_r0031` the per-event table moves 0.07–0.46 m (per-OM median) away
from the run's median, worst OM 1.54 m, while the first 3000 events of the same run
show only millimetres — a short window measures nothing.  `geometry.oms()` therefore
demands `local_idx` for experimental data and refuses to hand out a run snapshot
unless asked explicitly; the MC detector is one static table.  Checked against the
hit positions of the HDF5 (an independent write path): 7.6 µm for data, 7.4 µm for
MC.

**Three deliberate differences from BARS**, all visible in the number: the light
path is used instead of the perpendicular distance (the legacy fit path's model,
kept as an option for comparisons); "empty" means *did not fire*, where BARS
excludes the channels its final track used (a pulse the fit dropped is "quiet" for
BARS and "fired" here); and when nothing in the window is silent the result is NaN
rather than BARS' sentinel `1e-9`.

**The check that the arithmetic is right.**  `validate_vs_bars.py` recomputes the
variable in the strict BARS reading — perpendicular distance, "empty = unused by
our final track" — twice: at our own track and at BARS' own track (`fMuonTrack`
from the ROOT file).  At BARS' track the median relative difference to
`fPnonHit` is **1.8–3.5e-7** (59–74% below 1e-6; the residue is the float32 the
branch stores).  At our track the same comparison gives 4.6e-4–1.9e-3, of the same
order as our `time_chi2` agreement (8.5e-4) — i.e. the difference is the fit's own,
not the tool's.

## Running it

```bash
python inference/track_fit_alike_bars/tests/test_fit.py           # 10 self-checks
python inference/track_fit_alike_bars/tests/test_isolation.py     # 6 self-checks
python inference/track_fit_alike_bars/tests/stage_diagnostics.py  # stage by stage
python -m inference.track_fit_alike_bars.validate_vs_bars --source exp_reco \
    --n-parts 200 --per-part 10 --workers 16
python -m inference.track_fit_alike_bars.validate_vs_bars --source mc_reco \
    --data-class muatm_2020 --n-parts 100 --per-part 10 --workers 16
```

The validation writes `inference/track_fit_alike_bars/validation/<YYMMDD_HHMM>/` with the
per-event table, a provenance sidecar and `summary.md`; the sidecars are not under git
(`*.json`), the summaries are.
